## 1. 系统架构与模块边界（已确认）

### 1.1 目标与范围

在 macOS 本机交付一套可实际使用的论文投稿基础数据管理系统。V0.1 包含：

- 单管理员初始化、登录、退出和密码修改。
- 用户、角色及作者授权的数据模型和后端权限检查。
- 作者、邮箱、单位及作者单位关系管理。
- 稿件、共同作者、署名顺序、稿件版本和文件版本管理。
- 出版社、投稿平台和期刊基础档案。
- 分层数据隔离、敏感字段动态裁剪和只追加审计。
- OpenAPI、Postman/Newman、pytest、Vitest 和交付验收。

V0.1 不包含：Playwright 业务自动化、Browser Use、AI Agent、LangGraph、邮箱同步、自动注册、自动投稿、投稿状态自动跟踪和 APScheduler。后续功能不得绕过本规格中的授权和审计边界。

### 1.2 运行环境

采用已确认的方案 1：

- 复用本机 Homebrew MySQL 8.0.42。
- Python 使用项目 `.venv`，当前为 Python 3.13.3。
- 通过 Homebrew 安装 Node.js，Vue 开发服务器本地运行。
- 备份加密工具使用 `age`，通过 Homebrew 安装；私钥保存在项目目录之外。

- Vite 将 `/api` 代理到 FastAPI；CORS 只接受显式配置的本地来源。
- MySQL 仅允许本机或受控连接，不暴露到公共网络。

### 1.5 认证与安全

- 首次管理员通过受控初始化命令创建，不设置代码内默认密码。
- 密码使用 Argon2id 哈希；首次登录后必须修改初始密码。`must_change_password=true` 时，后端只放行 `/auth/me`、`/auth/csrf`、`/auth/change-password` 和 `/auth/logout`，其他已认证业务接口返回 `403 PASSWORD_CHANGE_REQUIRED`。
- 登录成功生成至少 256 位随机 Session Token，数据库仅保存其 SHA-256 哈希。
- Cookie 名称为 `asa_session`，设置 `Path=/`、不设置 `Domain`，并包含 `HttpOnly`、`SameSite=Lax`；HTTPS 环境启用 `Secure`，本机 HTTP 开发使用显式的开发配置。
- CSRF 请求头固定为 `X-CSRF-Token`；Session Cookie 和 CSRF Token 都不得出现在 URL 查询参数中。
- 默认 30 分钟空闲过期、8 小时绝对过期，具体值可配置。
- 修改密码后撤销该用户全部 Session；退出立即撤销当前 Session。
- 所有已认证的修改类请求必须校验独立 CSRF Header 和可信 `Origin`。登录尚无 Session，只要求可信 Origin 和登录限速，不要求预存 CSRF Token。CORS 不能替代 CSRF。
- CSRF Token 使用服务端秘密对当前 Session 的令牌哈希进行 HMAC-SHA256 派生，在同一会话内稳定，登录和 `GET /auth/csrf` 可重复得到相同 Token；数据库仍只保存其哈希。派生秘密通过本机安全配置注入，不进入 Git。
- `GET /auth/csrf` 不轮换 Token，因此不会使其他标签页失效。前端收到 `SECURITY_CHECK_FAILED` 时可重新获取 Token，并仅在原请求未通过安全校验的前提下重试一次。
- 登录失败按用户名规范化值和来源地址限速，返回统一失败信息，避免账号枚举。
- 前端不在 LocalStorage 保存密码、Session Token、CSRF Token 或其他长期秘密。

### 1.6 前端页面

## 2. MySQL 数据库详细设计（已确认）

### 2.1 统一约定

- 共 18 张核心表，每张表只定义一次。
- 引擎 InnoDB，字符集 utf8mb4；普通资源主键为 `CHAR(36)` UUID。
- 联合主键仅用于 `user_roles` 等明确关联表。
- 时间使用 `DATETIME(6)`，应用和数据库 Session 均按 UTC 处理，前端转换为本地时区。
- 可变业务表包含 `created_at`、`updated_at`、`created_by`；不可变版本只包含创建信息。
- `created_by`、操作者和审计外键使用 `ON DELETE RESTRICT`；用户采用停用或软删除，历史操作者关联不得消失。
- 作者、稿件、账号类业务数据采用软删除。不可变版本不得更新内容或通过业务接口物理删除。
- 外键默认 `ON DELETE RESTRICT`，禁止级联清除审计和历史。
- JSON 字段必须由 Pydantic 验证内部结构，不能接受任意未校验对象。
- 关键唯一约束由数据库最终保证，Service 预检查只用于改善错误提示。

### 2.2 权限模型

用户身份、角色和作者授权是三个不同维度：

```text
users → roles / user_roles → author_authorizations
```

V0.1 预置角色代码：`system_admin`、`submission_operator`、`reviewer`、`author`、`auditor`。只初始化一名系统管理员，不开发多用户管理页面。

角色决定能力上限，作者授权决定可访问哪些作者。除系统管理员外，拥有角色不等于自动拥有任何作者数据权限：

| 角色 | V0.1 能力上限 |
|---|---|
| `system_admin` | 全部管理、授权和审计能力 |
| `submission_operator` | 在有效作者授权范围内执行作者和稿件读取、修改及文件操作 |
| `reviewer` | 只读；即使误配置写权限代码也不能执行写操作 |
| `author` | V0.1 不开放作者登录；预留本人授权范围内的只读能力 |
| `auditor` | 仅读取审计日志，不读取作者稿件或文件内容 |

后端同时检查角色能力上限和作者授权，两者取交集。`submission_operator` 的测试账号通过 Fixture 创建，不需要增加用户管理 UI。

多角色规则：用户有效且含有 `system_admin` 时，管理员能力明确优先；否则非管理员角色能力取并集，作者授权仍逐作者、逐权限检查。例如 `submission_operator + reviewer` 可以按有效授权写入，`auditor + submission_operator` 可以同时使用审计和获授权稿件能力。角色组合不得改变共同作者敏感字段规则。权限代码之间不存在隐式推导，写权限不自动包含读取权限。

作者授权权限代码由后端枚举定义：

| 权限 | 含义 |
|---|---|
| `manuscript:read` | 读取主作者名下稿件及最小署名信息 |
| `manuscript:create` | 创建主作者名下稿件 |
| `manuscript:update` | 修改稿件元数据、版本和署名 |
| `manuscript:file:manage` | 上传、下载和软删除稿件文件 |
| `author:profile:read` | 读取作者基本资料及单位名称 |
| `author:email:read` | 读取作者邮箱 |
| `author:phone:read` | 读取作者电话 |
| `author:address:read` | 读取作者详细地址 |
| `author:profile:update` | 修改作者个人资料 |

后续必须独立定义 `submission:prepare` 和 `submission:submit`，正式提交权限绝不能从稿件管理权限推定。客户端传入未知权限代码时返回 `422 VALIDATION_ERROR`。

有效授权必须同时满足：用户有效、作者有效、当前时间处于授权有效期、`revoked_at IS NULL`。同一作者多条有效授权的权限取并集；撤销一条不影响其他仍有效的授权，但任何失效权限不得继续使用。

### 2.3 分层隔离（方案 B）

核心原则：主作者的稿件管理授权不自动授予共同作者个人资料访问权限。

仅拥有主作者授权时：

| 操作或数据 | 结果 |
|---|---|
| 查看稿件标题、摘要和版本 | 按对应稿件权限允许 |
| 上传、下载稿件文件 | 按 `manuscript:file:manage` 允许；上传因返回元数据还需 `manuscript:read` |
| 查看共同作者姓名、署名顺序和通讯作者标记 | 允许最小必要信息 |
| 查看共同作者邮箱、电话、详细地址 | 禁止 |
| 修改共同作者个人资料 | 禁止 |

具体规则：

1. 稿件访问由 `manuscripts.owner_author_id` 的有效稿件授权决定。
2. 稿件接口中的共同作者只返回 `author_id`、`display_name`、`position`、`is_corresponding`。
3. 共同作者详细资料通过独立作者接口获取，并检查该作者的细粒度权限。
4. 新增共同作者时，操作员必须具有该作者的 `author:profile:read`，防止通过猜测 UUID 枚举作者。
5. 已关联共同作者的顺序调整或移除按主作者 `manuscript:update` 处理，并要求显式确认和审计。
6. 任何包含作者信息的响应均通过授权感知 Schema 动态裁剪。未授权字段整体省略，不返回原值、掩码值或长度信息。
7. 稿件版本快照只包含最小署名信息，不得保存并随后泄露未授权邮箱、电话或地址。
8. 后续投稿流程需要共同作者敏感资料时，返回缺失授权清单并暂停，不能自动跳过期刊必填项。
9. 无权获知的资源统一返回 `404`；已知资源上的明确越权操作返回 `403`。

权限判断逻辑必须支持传入具体操作权限，不能用统一的 `can_access` 同时保护读取和写入：

```text
def has_author_permission(user, author_id, permission, now_utc):
    if not user.is_active:
        return False
    if user.is_system_admin:
        return True
    if not role_allows(user, permission):
        return False
    return authorization_repository.any_active(
        user_id=user.id,
        author_id=author_id,
        permission=permission,
        now_utc=now_utc,
        user_status="active",
        author_status="active",
    )


def can_access_manuscript(user, manuscript, permission="manuscript:read"):
    return has_author_permission(
        user=user,
        author_id=manuscript.owner_author_id,
        permission=permission,
        now_utc=utc_now(),
    )


def can_read_author_email(user, author):
    return has_author_permission(
        user=user,
        author_id=author.id,
        permission="author:email:read",
        now_utc=utc_now(),
    )
```

`any_active` 必须在数据库查询中检查权限代码、`valid_from <= now`、`valid_to > now`、`revoked_at IS NULL`，并联查用户和作者有效状态。不能只在 Python 中缓存长期授权结果。V0.1 不支持永久授权；创建或修改授权时，`valid_to` 必须是非空的有限时间，并晚于当前时间及 `valid_from`。

资源访问错误策略：

| 情况 | 响应 |
|---|---|
| 从未存在对应作者授权，或资源不属于该作者 | `404 RESOURCE_NOT_FOUND` |
| 存在授权记录但未生效、过期、撤销，或关联主体失效 | `403 AUTHORIZATION_EXPIRED` |
| 授权有效但缺少本次操作权限 | `403 PERMISSION_DENIED` |
| 角色能力上限禁止该操作 | `403 PERMISSION_DENIED` |
| CSRF 或 Origin 失败 | `403 SECURITY_CHECK_FAILED`，不进入资源查询 |

### 2.4 表结构

以下未重复说明的审计时间字段遵循 2.1。`JSON` 均为 MySQL JSON；`TEXT` 不保存秘密。

#### 1. `users`

| 字段 | 类型与规则 |
|---|---|
| `id` | UUID 主键 |
| `username` | `VARCHAR(64)`，保留管理员输入的显示形式 |
| `normalized_username` | `VARCHAR(64)`，去空格并小写，唯一 |
| `display_name` | `VARCHAR(128)` |
| `password_hash` | `VARCHAR(255)`，仅 Argon2id 哈希 |
| `status` | `VARCHAR(32)`：`active` / `disabled` |
| `must_change_password` | Boolean，初始化时为 true |
| `last_login_at` | `DATETIME(6)`，可空 |
| `created_at` / `updated_at` / `created_by` / `deleted_at` | 通用字段 |

索引：`status`。

#### 2. `roles`

- `id` UUID 主键。
- `code VARCHAR(64)` 唯一。
- `name VARCHAR(128)`、`description VARCHAR(500)`。
- 通用创建和更新时间字段。

#### 3. `user_roles`

- `(user_id, role_id)` 联合主键，分别外键到用户和角色。
- `assigned_by CHAR(36)` 外键到用户，可空用于初始化。
- `created_at DATETIME(6)`。

#### 4. `auth_sessions`

| 字段 | 类型与规则 |
|---|---|
| `id` | UUID 主键 |
| `token_hash` | `CHAR(64)` 唯一，原始令牌不入库 |
| `csrf_token_hash` | `CHAR(64)` |
| `user_id` | 用户外键 |
| `created_at` / `last_seen_at` | `DATETIME(6)` |
| `idle_expires_at` / `absolute_expires_at` | `DATETIME(6)` |
| `revoked_at` | `DATETIME(6)`，可空 |

索引：`(user_id, revoked_at)`、`absolute_expires_at`。登录和修改密码时不得复用旧 Session。

#### 5. `authors`

| 字段 | 类型与规则 |
|---|---|
| `id` | UUID 主键 |
| `given_name` / `middle_name` / `family_name` | `VARCHAR(128)`；given/family 可空以支持单名，display 必填 |
| `display_name` | `VARCHAR(255)` |
| `alternate_names` | JSON 数组，每项含语言及各姓名部分 |
| `orcid` | `CHAR(19)`，可空、唯一 |
| `phone_country_code` | `VARCHAR(16)`，可空 |
| `phone_number` | `VARCHAR(32)`，可空 |
| `status` | `VARCHAR(32)`：`active` / `inactive` |
| `notes` | TEXT，可空 |
| 通用字段 | 创建、更新、创建人、软删除 |

ORCID 接受标准 ID 或 ORCID URL，入库前移除 URL 前缀、规范为大写连字符形式，并验证格式和 MOD 11-2 校验位。多个 NULL 允许，非 NULL 唯一。

#### 6. `author_emails`

| 字段 | 类型与规则 |
|---|---|
| `id` | UUID 主键 |
| `author_id` | 作者外键 |
| `email` | `VARCHAR(254)`，原始显示形式 |
| `normalized_email` | `VARCHAR(254)`，去首尾空格并小写 |
| `purpose` | `VARCHAR(32)`：`communication` / `registration` / `backup` |
| `is_primary` | Boolean |
| `verification_status` | `VARCHAR(32)`：`unverified` / `verified` |
| `authorization_status` | `VARCHAR(32)`：`unconfirmed` / `authorized` / `revoked` |
| 通用字段 | 创建、更新、创建人、软删除 |

约束：`(author_id, normalized_email)` 唯一；`normalized_email` 普通索引。使用 STORED 生成列 `active_primary_author_id`：仅当 `is_primary = 1 AND deleted_at IS NULL` 时等于 `author_id`，否则为 NULL；对该生成列建立唯一索引，保证每位作者最多一个有效主邮箱。恢复软删除记录时如发生冲突返回 `409 CONFLICT`。

#### 7. `institutions`

- `id` UUID 主键。
- `name VARCHAR(255)`、`normalized_name VARCHAR(255)`。
- `institution_type VARCHAR(32)`，可空。
- `website_url VARCHAR(1024)`，可空。
- `address_line1`、`address_line2`、`city`、`region`、`postal_code`。
- `country_code CHAR(2)`，可空，使用 ISO 3166-1 alpha-2。
- 通用创建、更新、创建人和软删除字段。

索引：`(normalized_name, country_code, city)`。不强制单位名称全局唯一，避免误合并同名不同地单位；用户必须显式选择已有单位或创建新单位。

#### 8. `author_institutions`

- `id` UUID 主键。
- `author_id`、`institution_id` 外键。
- `department VARCHAR(255)`、`position_title VARCHAR(255)`，可空。
- `valid_from DATE`、`valid_to DATE`，可空；结束日期不得早于开始日期。
- `is_current` Boolean、`display_order INT`。
- 通用创建、更新、创建人和软删除字段。

索引：`(author_id, display_order)`、`institution_id`。允许一个作者有多个当前单位。单位名称按 `author:profile:read` 控制，详细地址按 `author:address:read` 控制。

| 字段 | 类型与规则 |
|---|---|
| `id` | UUID 主键 |
| `author_id` / `user_id` | 作者和被授权用户外键 |
| `permissions` | JSON 字符串数组，后端枚举校验、去重 |
| `valid_from` / `valid_to` | `DATETIME(6)`，均必填；结束时间必须晚于开始时间，V0.1 不允许 NULL 或永久授权 |
| `revoked_at` | `DATETIME(6)`，可空 |

| `notes` | TEXT，可空 |
| `reviewed_by` / `reviewed_at` | 审核人及时间，可空 |
| 通用字段 | 创建、更新、创建人；授权通过撤销失效，不物理删除 |

索引：`(author_id, user_id)`、`(valid_from, valid_to)`、`revoked_at`。

| 字段 | 类型与规则 |

| `abstract` | TEXT |
| `keywords` | JSON 字符串数组 |

#### 11. `manuscript_authors`

- `id` UUID 主键。
- `manuscript_id`、`author_id` 外键。

- `is_corresponding` Boolean。
- 通用创建、更新和创建人字段。该表表示当前署名关系；整体替换允许物理删除已移除的当前关联行，历史署名由不可变版本快照和 `operation_logs` 的最小前后摘要保存。

约束：`(manuscript_id, author_id)` 唯一、`(manuscript_id, position)` 唯一、`position > 0`。Service 保证顺序连续、主作者在列表中、至少一名通讯作者。

#### 12. `manuscript_versions`

- `id` UUID 主键。
- `manuscript_id` 外键。
- `version_number INT`。
- `label VARCHAR(100)`、`change_note TEXT`，可空。
- `metadata_snapshot JSON`。
- `created_at`、`created_by`，无普通更新接口。

约束：`(manuscript_id, version_number)` 唯一；`(manuscript_id, id)` 唯一，供当前版本和文件版本复合外键使用。快照包含稿件元数据及最小署名列表，不包含共同作者敏感资料。

#### 13. `file_families`

### 2.5 关键迁移顺序

1. 创建用户、角色、认证和作者基础表。
2. 创建 `manuscripts`，保留 `current_version_id` 列但暂不加当前版本外键。
3. 创建 `manuscript_authors` 和 `manuscript_versions`，建立 `(manuscript_id, id)` 唯一索引。
4. 为 `manuscripts (id, current_version_id)` 添加到 `manuscript_versions (manuscript_id, id)` 的复合外键。
5. 创建文件族，再使用复合外键创建文件表。
6. 创建其余业务表和审计表，最后验证全部索引与约束。

历史迁移一旦在共享或正式环境成功执行，不得直接修改；结构调整必须新增迁移版本。重复执行 `upgrade head` 不得重复创建结构或产生副作用。

## 3. API 接口规范与前后端交互

> 状态：接口分组和通用规则已确认；本节字段级定义在本次规格中补全，待用户书面审阅。

### 3.1 通用契约

- Base URL：`/api/v1`。
- 除文件上传、下载外均使用 `application/json`。
- 创建成功返回 `201`，普通读取和修改返回 `200`，无响应体的退出、改密和软删除返回 `204`。
- 列表参数：`page >= 1`、`1 <= page_size <= 100`、`sort`、`order=asc|desc` 及业务筛选；每个接口的 `sort` 只能使用服务端白名单字段。
- 列表响应：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 0
}
```

- 所有时间使用带 `Z` 的 ISO 8601 UTC；ID 使用 UUID 字符串。
- 服务端始终生成 UUID Request ID，并通过响应 Header `X-Request-ID` 和错误响应返回；客户端传入的 Request ID 不作为可信关联标识。
- 除登录外，已认证写操作在 OpenAPI 中明确标记需要 CSRF Header 和 Origin；登录只标记 Origin 要求。
- 权限代码不互相推导。写接口若返回既有资源内容，必须同时检查对应读取权限；若不要求读取权限，则只能返回 204 或不含受保护内容的最小结果。
- 错误响应统一为顶层结构，不再使用此前的 `error` 包装：

```json
{
  "code": "PERMISSION_DENIED",
  "message": "当前用户无权执行此操作",
  "request_id": "request-uuid",
  "details": null
}
```

字段校验错误的 `details` 只包含字段名和安全错误原因，不包含原始敏感值。

### 3.2 错误码

| HTTP | 业务错误码 | 场景 |
|---|---|---|
| 401 | `UNAUTHORIZED` | 未登录、Session 过期或撤销、登录失败 |
| 403 | `SECURITY_CHECK_FAILED` | CSRF 或 Origin 校验失败 |
| 403 | `PERMISSION_DENIED` | 明确无权执行操作 |
| 403 | `PASSWORD_CHANGE_REQUIRED` | 初始密码未修改，只允许改密相关认证接口 |
| 403 | `AUTHORIZATION_EXPIRED` | 授权未生效、过期、撤销或关联主体失效 |
| 404 | `RESOURCE_NOT_FOUND` | 资源不存在或不允许用户获知其存在 |
| 409 | `CONFLICT` | 唯一约束或并发冲突 |
| 409 | `INVALID_MANUSCRIPT_STATE` | 稿件或版本状态不允许操作 |
| 413 | `FILE_TOO_LARGE` | 文件超过限制 |
| 415 | `UNSUPPORTED_FILE_TYPE` | 扩展名、MIME 或实际内容不支持 |
| 422 | `VALIDATION_ERROR` | 输入或业务字段校验失败 |
| 429 | `TOO_MANY_ATTEMPTS` | 登录尝试过多 |
| 503 | `DATABASE_UNAVAILABLE` | 数据库不可用 |
| 500 | `INTERNAL_SERVER_ERROR` | 未预期异常，不返回堆栈 |

### 3.3 公共资源结构

#### 作者

`AuthorCreate` / `AuthorUpdate` 字段：

- `given_name`、`middle_name`、`family_name`、`display_name`。
- `alternate_names`：姓名变体数组。
- `orcid`：接受标准 ID 或 URL，响应只返回规范形式。
- `phone_country_code`、`phone_number`。
- `status`、`notes`。

创建只强制要求非空 `display_name`，允许 given/family 均为空以支持单名作者。创建和 PATCH 请求必须携带 `confirm_identity_change: true`，否则返回 `422 VALIDATION_ERROR`；该确认不能代替权限检查。PATCH 只更新显式提供的字段，确认参数不作为作者字段持久化。`AuthorResponse` 不嵌入邮箱或单位列表；电话字段仅在具有 `author:phone:read` 时出现，管理员例外。直接作者读取要求 `author:profile:read`；PATCH 同时要求 `author:profile:update` 和 `author:profile:read`，避免通过写响应读取未授权资料。

#### 稿件最小作者结构

```json
{
  "author_id": "uuid",
  "display_name": "Author Name",
  "position": 1,
  "is_corresponding": true
}
```

该结构是稿件接口唯一允许返回的共同作者信息，不包含邮箱、电话、ORCID、地址或个人备注。

#### 稿件

`ManuscriptCreate` / `ManuscriptUpdate`：

- `owner_author_id`（创建必填，创建后不可直接 PATCH）。
- `title`、`abstract`、`keywords`、`article_type`、`subject_field`、`language`。
- `funding_statement`、`conflict_of_interest_statement`、`ethics_statement`、`data_availability_statement`。
- `notes`。
- 创建时可传 `authors` 署名输入数组；省略时默认主作者为第 1 位通讯作者。

`ManuscriptAuthorInput` 只接受 `author_id`、`position`、`is_corresponding`，创建和署名 PUT 使用相同输入结构。客户端不能提交或覆盖 `display_name`；姓名由服务端读取作者记录后生成，只出现在 `ManuscriptAuthorResponse` 中。

`ManuscriptResponse` 增加只读字段：`id`、`internal_number`、`status`、`current_version_id`、`created_at`、`updated_at`。`authors` 仅使用最小作者结构。读取检查 `manuscript:read`；创建返回完整响应，因此同时要求 `manuscript:create` 和 `manuscript:read`；修改、署名变更及创建版本同时要求 `manuscript:update` 和 `manuscript:read`。返回 204 的软删除只要求 `manuscript:update`，不返回受保护内容。

#### 稿件版本

`ManuscriptVersionCreate`：`label`、`change_note`。响应包含 `id`、`manuscript_id`、`version_number`、`metadata_snapshot`、`created_at`、`created_by`。快照中的作者仍只允许最小作者结构。

#### 文件元数据

`FileResponse` 包含：`id`、`file_family_id`、`manuscript_id`、`manuscript_version_id`、`file_type`、`display_name`、`file_version`、`original_filename`、`mime_type`、`extension`、`size_bytes`、`sha256`、`scan_status`、`integrity_status`、`status`、`created_at`、`uploaded_by`。不返回 `storage_path` 或服务端绝对路径。

#### 用户与登录

| Schema | 字段 |
|---|---|
| `LoginRequest` | `username`、`password`，均为必填字符串 |
| `UserResponse` | `id`、`username`、`display_name`、`roles`、`status`、`must_change_password`、`last_login_at` |
| `LoginResponse` | `user: UserResponse`、`csrf_token`、`idle_expires_at`、`absolute_expires_at` |
| `ChangePasswordRequest` | `current_password`、`new_password` |

认证响应不包含 `password_hash`、Session Token 哈希、CSRF 哈希或其他用户的授权记录。

#### 邮箱与单位

| Schema | 字段与规则 |
|---|---|
| `EmailCreate` | `email`、`purpose=communication`、`is_primary=false`，以及必填且只能为 `true` 的 `confirm_email_binding` |
| `EmailUpdate` | 可选 `email`、`purpose`、`is_primary`；地址变更时 `confirm_email_binding` 必填且只能为 `true`；管理员还可修改 `verification_status`、`authorization_status` |
| `EmailResponse` | `id`、`author_id`、`email`、`normalized_email`、`purpose`、`is_primary`、两个状态字段、创建和更新时间 |

| `InstitutionResponse` | 仅系统管理员可用的完整单位字段及 ID、创建和更新时间 |
| `AuthorInstitutionLinkCreate` | `institution_id`、`department`、`position_title`、`valid_from`、`valid_to`、`is_current`、`display_order` |

#### 作者授权

`AuthorizationCreate`：

```json
{
  "author_id": "uuid",
  "user_id": "uuid",
  "permissions": ["manuscript:read", "manuscript:file:manage"],
  "valid_from": "2026-11-04T00:00:00Z",
  "valid_to": "2027-11-04T00:00:00Z",
```

`AuthorizationResponse` 包含上述字段及 `id`、`revoked_at`、`reviewed_by`、`reviewed_at`、`created_at`、`updated_at`、`validity_status`。`validity_status` 为 `not_yet_active`、`active`、`expired`、`revoked` 或 `inactive_subject`，由服务端计算，不接受客户端直接设置。权限数组去重并排序，空数组返回 `422`。

#### 出版社、平台与期刊

| Schema | 字段 |
|---|---|
| `PublisherCreate` / `PublisherResponse` | `name`、`website_url`、`notes`；响应增加 ID 和时间 |
| `JournalPlatformCreate` / `JournalPlatformResponse` | `code`、`name`、`description`、`status`；响应增加 ID 和时间 |
| `JournalCreate` / `JournalUpdate` | `publisher_id`、`platform_id`、`name`、`issn`、`eissn`、三个 URL、`subject_categories`、`article_types`、`requirements`、`requirements_source_url`、`requirements_verified_at`、`status`、`notes` |

URL 只允许 `https`，本机开发资料可显式允许 `http://127.0.0.1` 或 `http://localhost`；拒绝 `javascript:`、用户信息段和不支持的 scheme。ISSN 在响应中使用去连字符的 8 位规范形式，前端负责显示连字符。

#### 审计与仪表盘

`AuditLogResponse` 包含：`id`、`actor_user_id`、`actor_type`、`category`、`action`、`target_type`、`target_id`、`author_id`、`request_id`、`result`、脱敏前后摘要、`error_code`、`error_message`、`created_at`。不得因为管理员查询而把数据库中其他敏感表字段拼入响应。

`DashboardSummary` 包含 `author_count`、`manuscript_count`、`current_version_file_count`、`expiring_authorization_count` 和 `recent_operations`。`recent_operations` 只包含当前用户本人可知的操作类型、对象 ID、结果和时间，不包含敏感值。

#### Schema 通用校验

- 所有请求模型拒绝未知字段，避免把拼写错误或越权字段静默忽略。
- PATCH 至少包含一个可修改字段；路径 ID 与请求体中的关联 ID 必须一致。
- 字符串按字段规则去除首尾空白，长度上限与数据库一致；不得自动截断密码或令牌。
- `keywords` 最多 50 项、每项最多 200 字符；`alternate_names` 最多 20 项；单篇稿件作者最多 200 人。
- `permissions` 最多包含后端定义的全部权限代码，不允许空字符串、重复项或未知代码。
- `requirements` 最多 200 项，每项必须包含 `key`、`value`、`scope`、`source_url`、`verified_at`。
- 响应模型禁止透传 ORM 对象的动态属性；未授权敏感字段必须整体省略。

### 3.4 健康检查与认证

| 方法与路径 | 请求与响应 | 权限 |
|---|---|---|
| `GET /health` | 返回 `{status: "ok"}` | 本机公开 |
| `GET /health/ready` | 检查数据库，返回就绪或 503 | 本机公开，不返回连接细节 |
| `POST /auth/login` | `{username, password}`；返回用户、过期时间、`must_change_password`、`csrf_token`，并设置 Cookie | 公开、可信 Origin、限速，不要求预存 CSRF |
| `POST /auth/logout` | 撤销当前 Session，204 | 已登录、CSRF |
| `GET /auth/me` | 当前用户、角色和 `must_change_password` | 已登录 |
| `GET /auth/csrf` | `{csrf_token}` | 已登录 |
| `POST /auth/change-password` | `{current_password, new_password}`；撤销该用户全部 Session，204 | 已登录、CSRF |

新密码长度为 12–128 个字符，不得等于用户名或命中本地常见弱密码列表；接口不返回密码或哈希。改密后前端跳转登录页。

### 3.5 作者、邮箱和单位

| 方法与路径 | 行为 |
|---|---|
| `GET /authors` | 分页、按姓名/ORCID/状态筛选，只列出有 `author:profile:read` 的作者 |
| `POST /authors` | 系统管理员创建，要求身份确认参数；记录审计 |
| `GET /authors/{author_id}` | 按权限返回作者字段 |
| `PATCH /authors/{author_id}` | 同时要求 `author:profile:update` 和 `author:profile:read`；电话响应仍按电话权限裁剪 |
| `DELETE /authors/{author_id}` | 系统管理员软删除/停用；保留历史，204 |
| `GET /authors/{author_id}/emails` | 要求 `author:email:read` |
| `POST /authors/{author_id}/emails` | 同时要求 `author:profile:update` 和 `author:email:read`；`confirm_email_binding` 为必填 true，不得默认 |
| `PATCH /authors/{author_id}/emails/{email_id}` | 同时要求资料更新和邮箱读取权限；仅管理员可修改验证及授权状态 |
| `DELETE /authors/{author_id}/emails/{email_id}` | 同时要求资料更新和邮箱读取权限；请求体必须含 `{"confirm_email_binding": true}`，软删除，204 |
| `GET /institutions` | `system_admin`、`submission_operator`、`reviewer` 可读；非管理员只返回 `InstitutionSummaryResponse`，不含详细地址或作者关联 |
| `POST /institutions` | 系统管理员创建单位 |
| `GET /institutions/{institution_id}` | 非管理员同样只返回摘要；完整 `InstitutionResponse` 仅系统管理员可用 |
| `PATCH/DELETE /institutions/{institution_id}` | 系统管理员修改或软删除单位 |
| `GET /authors/{author_id}/institutions` | 要求 `author:profile:read`；详细地址按 `author:address:read` 裁剪 |
| `POST /authors/{author_id}/institutions` | 同时要求 `author:profile:update` 和 `author:profile:read`；单位必须有效且未删除 |
| `PATCH /authors/{author_id}/institutions/{link_id}` | 同时要求资料更新和读取权限；修改关联，不直接修改单位基础资料 |
| `DELETE /authors/{author_id}/institutions/{link_id}` | 要求 `author:profile:update`，软删除关联，204 |

邮箱创建、地址变更和解绑必须显式确认，确认参数不代替权限检查。邮箱创建和修改先规范化再执行唯一约束。主邮箱冲突返回 `409 CONFLICT`，不能静默取消另一个主邮箱。

### 3.6 作者授权

V0.1 授权管理仅系统管理员可用：

| 方法与路径 | 行为 |
|---|---|
| `GET /author-authorizations` | 按作者、用户、权限和有效状态筛选 |
| `POST /author-authorizations` | `{author_id, user_id, permissions, valid_from, valid_to, evidence_ref?, notes?}`，201 |
| `GET /author-authorizations/{id}` | 返回授权详情，不暴露凭证内容 |
| `PATCH /author-authorizations/{id}` | 修改有效期、权限、凭证引用和备注；记录前后权限代码，不记录敏感资料 |
| `POST /author-authorizations/{id}/revoke` | `{reason?}`，设置 `revoked_at`，返回更新后的授权 |

授权修改和撤销立即生效，已有 Session 不缓存长期授权结果。

### 3.7 稿件、作者顺序和版本

| 方法与路径 | 行为 |
|---|---|
| `GET /manuscripts` | 只列出当前用户具有 `manuscript:read` 的主作者稿件 |
| `POST /manuscripts` | 创建稿件、署名和初始 v1，同一事务完成，201 |
| `GET /manuscripts/{id}` | 返回工作元数据、当前版本和最小署名信息 |
| `PATCH /manuscripts/{id}` | 修改工作元数据，不改写历史版本 |
| `DELETE /manuscripts/{id}` | 软删除稿件，历史版本与文件仍保留，204 |
| `GET /manuscripts/{id}/authors` | 返回最小署名数组 |
| `PUT /manuscripts/{id}/authors` | 整体替换有序署名，要求显式确认 |
| `GET /manuscripts/{id}/versions` | 分页列出版本 |
| `POST /manuscripts/{id}/versions` | 锁定稿件、递增版本、保存快照并更新当前版本，201 |
| `GET /manuscripts/{id}/versions/{version_id}` | 读取指定不可变版本 |

本组读取操作检查 `manuscript:read`，写操作检查对应的创建或更新权限。创建稿件、PATCH、署名 PUT 和创建版本因返回受保护内容，还必须同时具有 `manuscript:read`；返回 204 的软删除只要求 `manuscript:update`。软删除稿件不物理删除版本或文件。

署名 PUT 请求：

```json
{
  "authors": [
    {"author_id": "uuid", "position": 1, "is_corresponding": true},
    {"author_id": "uuid", "position": 2, "is_corresponding": false}
  ],
  "confirm_authorship_change": true
}
```

顺序必须连续且从 1 开始，作者不得重复，主作者必须保留，至少一名通讯作者。新加入作者要求当前用户对其具有 `author:profile:read`。确认参数不能代替权限检查。Service 在稿件行锁内先保存最小署名前后摘要，再删除旧当前关联并插入新有序列表，避免交换位置时触发临时唯一冲突；版本快照和审计保留历史。

### 3.8 文件

| 方法与路径 | 行为 |
|---|---|
| `GET /manuscripts/{id}/versions/{version_id}/files` | 列出该版本文件元数据，要求 `manuscript:read` |
| `POST /manuscripts/{id}/versions/{version_id}/files` | 上传新文件或文件族新版本，同时要求 `manuscript:file:manage` 和 `manuscript:read`，201 |
| `GET /files/{file_id}` | 文件元数据，要求 `manuscript:read` |
| `GET /files/{file_id}/download` | 重新鉴权、完整性和路径校验后下载，要求 `manuscript:file:manage` |
| `DELETE /files/{file_id}` | 软删除文件记录，不抹除历史内容，要求 `manuscript:file:manage`，204 |

上传为 `multipart/form-data`：

- `file` 必填。
- 新文件族：`file_type`、`display_name` 必填，不传 `file_family_id`。
- 已有文件族：传 `file_family_id`；如同时传 `file_type` 或 `display_name`，必须与原文件族一致。
- 只允许向当前版本上传；历史版本可读取和下载。
- 默认单文件上限 100 MiB，配置值不得超过服务端硬上限 500 MiB。
- V0.1 扩展名白名单为 `.pdf`、`.doc`、`.docx`、`.rtf`、`.txt`、`.tex`、`.csv`、`.xls`、`.xlsx`、`.png`、`.jpg`、`.jpeg`、`.tif`、`.tiff`；扩展名、声明 MIME 和实际内容必须匹配。
- 禁止可执行文件、HTML、SVG、脚本和 ZIP 等通用压缩包。DOCX/XLSX 等 OOXML 文件虽使用 ZIP 容器，但属于允许类型，必须验证 OOXML 结构，并检查解压后总大小、条目数量和压缩比；默认总解压大小不超过 500 MiB、不超过 2,000 个条目、单条目压缩比不超过 100:1，禁止嵌套 ZIP 或 OOXML 容器。

下载统一使用安全 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`，文件名进行 CR/LF 和路径字符清理。正式文件缺失或完整性异常时禁止下载并返回冲突错误。

### 3.9 出版社、平台和期刊

出版社、平台和期刊均提供：

- `GET /{resource}`：分页和筛选。
- `POST /{resource}`：创建，201。
- `GET /{resource}/{id}`：读取。
- `PATCH /{resource}/{id}`：修改。
- `DELETE /{resource}/{id}`：软删除，204。

实际路径资源名为 `publishers`、`journal-platforms`、`journals`。出版社字段为名称和官网；平台字段为代码、名称、说明和状态；期刊字段对应 2.4 的期刊表。V0.1 这些档案仅系统管理员可写，`system_admin`、`submission_operator`、`reviewer` 可读；`auditor` 不能读取。期刊要求必须保留来源 URL 和核验时间，不能将一次整理永久视为准确。

### 3.10 仪表盘和审计

`GET /dashboard/summary` 仅供 `system_admin`、`submission_operator`、`reviewer` 使用，返回按当前用户授权过滤后的作者数、稿件数、当前版本文件数、即将到期授权数和当前用户本人最近操作摘要；不返回无权作者的计数或详情，也不向普通操作员或 `auditor` 开放完整审计查询。`auditor` 调用该接口返回 `403 PERMISSION_DENIED`。

`GET /audit-logs` 支持操作者、作者、类别、动作、对象、结果、Request ID 和时间范围筛选；`GET /audit-logs/{id}` 返回单条日志。仅 `system_admin` 和 `auditor` 可读，任何角色均无普通修改或删除 API。

## 4. 数据流、异常处理与审计（已确认）

### 4.1 请求顺序

```text
HTTP Request
  → 服务端生成或严格校验 Request ID
  → Session 认证
  → Origin / CSRF 校验（修改类请求）
  → Pydantic 输入校验
  → Service 角色权限检查
  → Service 作者授权及资源归属检查
  → 数据库事务
      ├── 业务数据变更
      └── 写入 operation_logs
  → 提交事务
  → 专用 Response Schema
  → 根据授权动态裁剪敏感字段
  → HTTP Response
```

关键业务变更与审计必须在同一事务中，审计写入失败则业务操作失败。资源读取和越权统一经过资源访问策略，防止通过错误差异探测其他作者资料。

### 4.2 文件一致性

文件系统与 MySQL 不构成真正原子事务，按补偿和核查处理：

| 场景 | 处理 |
|---|---|
| 临时文件写入失败 | 删除临时文件 |
| 文件校验失败 | 删除临时文件 |
| 正式文件移动失败 | 回滚数据库事务并清理临时文件 |
| 移动成功、已确定数据库回滚且文件记录不存在 | 尝试清理正式文件，清理失败则登记核查 |
| 移动成功、提交结果不确定或连接中断 | 保留正式文件并登记核查；重新连接后按文件 ID 和存储路径对账，只有确认无数据库记录时才允许补偿删除 |
| 移动成功、进程突然崩溃 | 后台核查并标记孤立文件，不自动删除未知文件 |
| 数据库有记录、正式文件不存在 | 标记 `missing`，禁止下载 |
| 哈希不一致 | 标记 `hash_mismatch`，禁止下载 |

临时目录和正式目录必须位于同一文件系统以支持原子重命名。上传流程为：鉴权 → 流式写临时文件 → 大小和 SHA-256 → 扩展名、MIME 和文件魔数检查 → 开启事务并锁定稿件行 → 重新检查稿件状态及 `version_id == current_version_id` → 锁定文件族并生成版本和文件 ID → 原子移动 → 提交事务 → 按确定回滚或结果不确定分别补偿。所有文件操作统一采用“稿件 → 文件族”的锁顺序；版本不匹配时返回 `409 INVALID_MANUSCRIPT_STATE` 并清理临时文件。提交结果不确定时不得直接删除正式文件。

文件路径完全由服务端生成，目录只含内部 ID。V0.1 未接入杀毒引擎时标记 `not_scanned`，不得声称为安全文件。清理和孤立文件核查通过显式管理命令执行，不引入 APScheduler。清理脚本只自动删除达到保留期限的已知临时文件；正式目录未知文件进入人工核查清单。

### 4.3 并发与重试

- 稿件元数据或署名修改与版本创建都在事务内锁定同一稿件行，保证快照内容和当前版本指针一致。
- 创建稿件版本时锁定稿件行，依赖 `(manuscript_id, version_number)` 唯一约束。
- 上传文件版本时先锁定稿件行并重新验证当前版本，再锁定文件族，依赖 `(file_family_id, file_version)` 唯一约束；统一锁顺序以避免与版本创建相互竞态。
- 主邮箱由生成列唯一索引最终保证。
- 唯一冲突映射为 `409 CONFLICT`，不得静默覆盖或改变其他记录。
- GET 可由客户端有限退避重试；修改类请求失败后先查询状态，不盲目重放。
- 数据库中断时回滚并停止外部操作，恢复后核对文件和数据库状态。

### 4.4 审计分类

| 类别 | 内容 |
|---|---|
| 认证审计 | 登录成功/失败、退出、改密、Session 撤销 |
| 授权审计 | 创建、修改和撤销作者授权，以及因未生效、过期或撤销而拒绝访问 |
| 业务审计 | 作者、稿件、署名、版本、文件、出版社、平台和期刊关键操作 |
| 敏感访问审计 | 邮箱、电话和详细地址读取 |

敏感访问记录访问者、作者、资料类别、时间和 Request ID，不记录实际值。列表请求只要实际返回了某作者的敏感字段，就为该作者和资料类别写入访问审计；同一请求共用 Request ID，未返回敏感字段的作者不产生敏感访问记录。审计写入失败时不得返回敏感资料。变更前后摘要采用字段白名单。禁止记录密码、Session、CSRF、Cookie、OAuth Token、完整验证链接、完整邮件正文和不必要的敏感个人资料。

应用日志用于排错，可按策略轮转；审计日志只追加并制定备份和保留策略。管理员也不能通过普通业务接口修改历史审计。

## 5. 测试、验收与交付（已确认）

### 5.1 测试隔离

- 使用独立 MySQL 测试数据库和独立临时文件目录，不使用 SQLite。
- `TEST_DATABASE_URL` 的数据库名必须以 `_test` 结尾，且 `ENVIRONMENT=test`；启动测试时再次检查连接目标，不满足即拒绝运行。
- 测试禁止指向开发数据库，文件测试禁止指向正式 `storage/`。
- Fixture 创建和清理数据，每个用例独立，不依赖执行顺序。
- 并发测试使用真实 MySQL 连接验证行锁和唯一约束；Fixture 数据必须先提交，再由两个独立连接访问，不能依赖外层未提交测试事务共享数据。
- 测试结束清理数据和临时文件；清理失败应使测试报告明确警告。

### 5.2 后端测试范围

1. Session、CSRF、Origin、改密和登录限速。
2. 有效、未生效、过期、撤销授权，以及用户或作者停用。
3. 分层隔离完整权限矩阵和最小作者响应。
4. 手工构造作者 ID、稿件 ID 的跨作者访问。
5. 邮箱规范化、唯一主邮箱和 ORCID 校验。
6. 稿件版本、当前版本归属、文件族归属和不可覆盖约束。
7. 文件魔数、MIME 伪装、路径穿越、超限、哈希和异常恢复。
8. 业务变更与审计同事务提交或回滚。
9. 统一错误结构和防资源枚举策略。

覆盖率目标：核心权限和授权逻辑 95%，文件管理核心逻辑 90%，Service 层 85%，API 层 80%，整体后端 80%。覆盖率只是辅助指标；权限绕过、敏感字段泄露和文件安全是独立验收项，不能因覆盖率达标而豁免。

### 5.3 必跑安全与一致性测试矩阵

| 用例 | 场景 | 必须断言 |
|---|---|---|
| AUTH-01 | 无 Session 或 Session 过期 | `401`，无业务数据返回 |
| AUTH-02 | 缺失/错误 CSRF 或不可信 Origin | `403 SECURITY_CHECK_FAILED`，数据库无变化 |
| AUTH-03 | 改密或退出后复用旧 Session | `401`，旧 Session 已撤销 |
| AUTH-04 | `must_change_password=true` 时访问业务 API | `403 PASSWORD_CHANGE_REQUIRED`，仅改密相关认证接口可用 |
| AUTH-05 | 两个标签页重复获取 CSRF Token | 同一会话 Token 稳定，双方修改请求均可通过校验 |
| ROLE-01 | 多角色组合及 reviewer 单独只读 | 管理员明确优先，非管理员能力取并集，作者授权仍生效 |
| AUTHZ-01 | 无任何作者授权时猜测作者/稿件 UUID | `404`，响应与不存在的资源不可区分 |
| AUTHZ-02 | 授权未生效、过期或撤销 | `403 AUTHORIZATION_EXPIRED` |
| AUTHZ-03 | 有读取权限但执行修改 | `403 PERMISSION_DENIED`，无业务数据变更；拒绝事件不含敏感值 |
| ISO-01 | 只有主作者稿件权限，读取含共同作者稿件 | 返回稿件和最小署名，无共同作者邮箱、电话、地址 |
| ISO-02 | 只有主作者权限，请求版本快照、文件列表和仪表盘 | 各响应均无共同作者敏感字段 |
| ISO-03 | 手工替换作者、稿件、版本、文件族或文件 UUID | 不返回跨作者数据，不执行操作 |
| ISO-04 | 新增未授权共同作者 | 操作被拒绝，不能通过响应判断该作者详细资料 |
| ISO-05 | 只有写权限、没有对应读取权限时调用返回资源内容的写接口 | 请求被拒绝，不能借创建或修改响应读取资源 |
| ISO-06 | 非管理员调用全局单位列表和详情 | 只返回选择所需摘要，不能绕过 `author:address:read` 获取详细地址 |
| FILE-01 | 扩展名、Content-Type 与文件魔数不一致 | `415`，临时文件清理，数据库无记录 |
| FILE-02 | 恶意文件名、路径穿越和 CR/LF | 服务端路径不受影响，下载 Header 安全 |
| FILE-03 | 两个真实连接并发上传同族文件 | 行锁使两个请求均成功，版本号为 1 和 2 且内容不覆盖；唯一冲突另测为 `409` |
| FILE-04 | 移动失败、确定回滚、提交结果不确定、孤立文件和正式文件缺失 | 按补偿矩阵处理；不确定提交先对账，不直接删除正式文件，异常文件禁止下载 |
| FILE-05 | 上传校验期间另一请求创建新稿件版本 | 上传在稿件锁内重新检查当前版本，旧版本上传返回 `409` |
| TX-01 | 审计插入失败 | 关键业务变更回滚，不出现半提交状态 |
| MIG-01 | 空库迁移后再次 `upgrade head` | 18 张表及约束正确，无重复副作用 |
| API-01 | 未登录、无授权、跨作者访问的 Newman 用例 | 状态码、错误码、响应结构和字段缺失同时通过 |
| WEB-01 | 浏览器检查共同作者稿件详情 | 界面和 Network 响应均不存在未授权敏感字段 |
| BACKUP-01 | 加密备份并恢复到独立测试环境 | 记录、文件和哈希一致，原开发环境未被覆盖 |

### 5.4 API、前端和异常测试

### 5.5 数据库迁移与备份恢复

迁移验收：

1. 从空数据库执行到 `head`。
2. 再执行一次 `upgrade head`，不得产生重复结构或副作用。
3. 验证外键、生成列、唯一索引和当前版本复合约束。
4. 已执行历史迁移不直接修改，结构变化新增版本。

备份恢复验收：

- 提供受控备份脚本，至少包含 MySQL 一致性导出、稿件文件、配置样例和带 SHA-256 的清单；不包含明文密码、Session 或可复用 Cookie。
- 备份在暂停业务写入后执行，并使用 `age` 加密；密钥不存入项目或 Git。
- 在独立测试数据库和独立恢复目录实际完成一次恢复，核对表数量、关键记录、文件数量和哈希。
- 恢复脚本默认禁止覆盖开发数据，必须显式指定目标并二次确认。
